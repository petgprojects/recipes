## The problem

Before this, the only way to send someone a recipe was the "Read the original
on …" link in the detail sheet — which sends them to *the source's* page and
loses everything this site adds: our own blurb, the parsed and canonicalised
ingredient lines, the shelf life, and a "Save it" button that puts the recipe in
the recipient's grocery list. There was no URL for a recipe on this site at all.
The detail sheet is client state inside `/`.

## Amendment A40 — the link key is a new column, not the slug and not the id

**The slug cannot be the key.** `apps/worker/src/scanner/text.ts` has said so
since Phase 1 — "not unique on its own" — and the corpus agrees: 425 recipes,
**419 distinct slugs**. `lemony-pasta-with-blistered-cherry-tomatoes-and-crispy-caper-crumbs`
appears three times and four other slugs appear twice. A link keyed on the slug
would resolve to whichever of the duplicates the query happened to return first,
and would do it silently.

**The id could be, and should not be.** `recipes.id` is a UUID: unique, but 36
characters in a link people paste into a text message, and a promise about our
own primary keys that there is no reason to make.

So: `recipes.share_code`, eight characters, unique, generated by a plpgsql
`gen_share_code()`. Four decisions inside that are worth keeping:

- **The alphabet is Crockford-shaped** — `0-9a-z` minus `i`, `l`, `o` and `u` —
  so a code read off a screenshot or over the phone cannot be misread, and a
  code is unlikely to spell anything. 32 symbols, and 256 % 32 = 0, so the
  byte-modulo draw is uniform rather than biased toward the front.
- **It is a column `DEFAULT`, not something the writer assigns.** That is what
  keeps the worker entirely out of this feature: JSON-LD extraction, the LLM
  extractor and the Reddit adapter all insert without naming the column and all
  get a code. Verified with a bare `INSERT … (source_id, source_url, title,
  slug, status)`, which came back with `egy4srt5`.
- **The generator retries on collision** rather than trusting 32^8 ≈ 1.1e12.
  It costs one indexed probe per insert and turns the collision this table will
  never see from a failed crawl into a second draw.
- **The backfill is one statement per row.** A single set-based
  `UPDATE … SET share_code = gen_share_code()` evaluates every call against a
  snapshot in which every code is still NULL, so the generator's uniqueness
  check would be checking against nothing. Separate statements inside one
  transaction see each other's writes.

The shape is enforced twice on purpose: `recipes_share_code_shape` in SQL and
`parseRecipeHandle()` in TypeScript. A code the database accepts and the parser
rejects is a link that 404s for no visible reason, so the two are written to
look alike and `share.test.ts` walks the whole alphabet across both.

## Amendment A41 — the slug in the URL is decoration, and that is the point

Resolution is on the **code alone**; the slug is for the human holding the link.
Two consequences, both deliberate:

- A recipe whose title Phase 2 rewrites keeps every link ever shared for it.
  The old handle still resolves, and the route `307`s to the current canonical
  one rather than rendering under words that are no longer true.
- `parseRecipeHandle()` takes the **last** hyphen-delimited segment and nothing
  else. A slug can contain any number of hyphens, and an eight-character
  code-shaped word inside one is perfectly possible; "last segment" is
  unambiguous where "the segment that looks like a code" is not.

A bare `/r/<code>` also resolves, with an empty slug, and redirects to canonical
— that is what a link truncated by whatever it was pasted into looks like.

## Amendment A42 — a share link renders the planner, not a second recipe page

`/r/<handle>` server-renders the existing planner with the existing detail sheet
already open. It does **not** introduce a second way to render a recipe.

The reason is the one `summaryColumns` exists for: two renderers for one recipe
drift, and the symptom would be a shared link missing a photo or a note that the
browse sheet shows. It also gives a shared link somewhere to go — close the
sheet and you are in the browse feed, not at a dead end.

Three things fell out of it:

- **The server load moved into `components/planner-page.tsx`**, shared by `/`
  and `/r/`. Whatever the server renders becomes the client's TanStack Query
  `initialData`, so a second copy differing by one argument would present as the
  feed reshuffling on load — but only on shared links.
- **The share lookup happens there, not in the route.** `getCurrentUser()` is
  not memoised per request and the reader's id is an argument to the lookup, so
  resolving it in the route would mean two session lookups per shared link.
- **`notFound()` and `redirect()` are called outside the `try`.** Both work by
  throwing. Inside it they would be caught by the database-failure handler and
  rendered as "can't reach the kitchen" with a `200`, where a `404` belongs.

## Amendment A43 — a share link ignores the recipient's hard rules

`getRecipeByShareCode()` is not filtered by the reader's Phase 7 hard rules.
Rules shape a *feed*; a share link is one specific recipe someone was sent, and
hiding it because the recipient filters out pork would present as a broken link
rather than as a preference. This is the same argument `FILTER_PLAN.md` §4.2
makes for search, which also bypasses them.

It **is** restricted to `status = 'active'`, and unlike every other read in
`lib/recipes.ts` there is no `status` option to widen that. Elsewhere the option
exists for `/ops` inspection; here it would let a link publish a rejected page,
or a pending one with no blurb and no category — exactly what
`recipes_active_enrichment_complete` keeps off the site.

## Amendment A44 — three share behaviours, because two of them are often absent

`ShareButton` prefers `navigator.share` (the real share sheet on a phone, and
the only path that does not make the reader paste it themselves), falls back to
`navigator.clipboard`, and falls back again to showing the URL pre-selected in a
read-only field.

The third is not padding. **Both APIs are gated on a secure context**, and this
app is routinely reached at `http://<lan-ip>:3000` — `localhost` is a secure
origin and a bare IP is not. On that origin the first two are simply missing,
and a share button that silently did nothing would be indistinguishable from a
broken one. `AbortError` from a dismissed share sheet returns quietly: declining
to share is a decision, and reporting "copied" there would announce something
the reader just refused.

The URL is built in the click handler from `window.location.origin`, never
rendered from `NEXT_PUBLIC_APP_URL` — the server does not know which host the
reader typed, and baking the env var into the markup would hand a `localhost`
link to someone browsing over the LAN. `NEXT_PUBLIC_APP_URL` is still what the
Open Graph tags use, because a crawler resolves relative URLs against nothing.

## Amendment A45 — closing the sheet leaves the share URL

`/r/<handle>` describes a sheet that is open. When it closes, the planner
`replaceState`s back to `/`. Left in place the URL would outlive what it
describes twice: a reload would reopen the sheet the reader just dismissed, and
`goToQuery()` would push `?q=` onto the share path instead of onto the planner.
`replaceState` and not `pushState` — closing a sheet is not a place to go back
to.

**Opening a sheet from the browse feed deliberately does not rewrite the URL.**
It would put the planner's URL state and the search's `?q=` state in contention
for the same address bar, and the share button already hands over the link on
request.
